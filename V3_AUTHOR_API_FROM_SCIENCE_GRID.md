# Author API derived from the numerical grid workflow

This pre-code audit uses v2.1 commit `61ed0067448658e02d181b3cb85d7f68e39b6616`. The numerical workflow qualifies a prospective cutoff, runs a detached CPU Job for each selected route, and asks separate workers to assess the measurements and choose the next round. A changed cutoff can produce a new evaluation from the original observations. A newly submitted source can require a fresh review before the project closes. These are the operations the author interface has to carry. [Grid definition](gx-h/workflows/science_grid_v2/v2.json) · [Node bindings](gx-h/workflows/science_grid_v2/__init__.py#L11) · [Source and review race tests](gx-h/tests/test_p0_review_sources.py)

## Registration

Registration runs once for an installed package identity. It only collects declarations. The Run acquires its own context when GX dispatches an actual callback. An installation can therefore serve two Runs concurrently without a cached Run ID or connection in module globals. The blueprint's sample combines registration and execution attributes on one protocol. The observed entrypoints have distinct lifetimes. [Reference protocol](GX_H_V3_Lean_Implementation_Package/contracts/author_api_reference.py) · [Registry bootstrap](gx-h/gx_core/orchestration/service.py#L100)

| Contribution | Minimum public input and owner handoff |
| --- | --- |
| Workflow | Accept an explicit reference to an existing registered graph, or a versioned graph declaration with named nodes, stage rules, product validator, completion evidence and relevant hook behavior. Preserve the full five-node graph. The host resolves reference-only registrations by the canonical pinned ID, version and digest. New graph implementations go through the same WorkflowRegistry. A manifest extension's contract ID/version and the target graph's ID/version are separate fields. [Build contract](gx-h/gx_core/orchestration/loader.py#L37) · [Registry immutability](gx-h/gx_core/orchestration/registry.py#L32) |
| Worker tool | Register its name, input schema and handler, scoped to the Run composition. GX binds the handler at the existing Root extension point and owns the callback receipt, artifact access list and attempt fence. The original grid returns **zero** extension tools. Its distinct behavior is the implementation behind the built-in `gx_task_context`. A composed grid can contribute a read of its assigned route measurements through `ctx.tools`, returning the proposal, original observation and frozen evaluation refs that the assessment already requires. Keep the built-in read, submit and wait names owned by Roots. [Actual grid hooks](gx-h/workflows/compat_v20/grid.py#L43) · [Built-ins and binding](gx-h/gx_core/p0/roots.py#L33) · [Extension callback](gx-h/gx_core/p0/roots.py#L779) |

| Evaluation | The grid already has a built-in frozen scorer and an optional Node/Cordis score evaluator. Both feed the same evaluation artifacts and ledger. The host binds Run, task, attempt, actor and current revision before entering the handler. A request cannot change that scope by supplying another ID in its body.

## Transaction boundaries that change the design

1. **Pure preparation and admission.** A transaction-bound hook receives named reads and controlled same-transaction domain mutations. The plugin API exposes neither a connection nor a transaction manager. The current storage helper creates savepoints on nested entry. Reusing such a helper blindly would create a nested transaction. Adapt the existing owner's operation to an already-open writer, or schedule the command at the existing outside-writer boundary. [SQLite transaction helper](gx-h/gx_core/persistence/store.py#L502) · [Stage checks at commit](gx-h/gx_core/orchestration/engine.py#L1539)
2. **Expensive work currently reaches a claim.** V2's dispatch hook calls `_new_review_inputs` after a criterion change. This can requalify three control cases, publish files, rescore original observations, enter Node/Cordis for an explicitly selected evaluator, create a replacement review and attach its dependency. A new transaction-bound handler must read prepared results and return ready/wait with a revision check. Prepare the evaluation and files through the existing evaluation/Artifact and Intent Outbox owners, outside the claim, keyed by original evaluation and item version. Retain source/criterion checks when the ready task is actually claimed. A previously frozen evaluator can be reused. [Grid dispatch](gx-h/gx_core/p0/science_refresh_v2.py#L69) · [Changed-review inputs](gx-h/gx_core/p0/science_refresh.py#L39) · [Control qualification](gx-h/gx_core/p0/science.py#L102) · [Existing Outbox consumer](gx-h/gx_core/p0/driver.py#L224)
3. **Stage and mechanical execution differ.** The engine invokes stage nodes outside the writer, then commits their result under its advance fence. Mechanical nodes, stage readiness and final validation run inside the writer. The existing Job wrapper explicitly requires an outside-writer call. For external effects use the stage/service boundary or existing Root compute proposal queue and its drain. For a new mechanical author callback that creates artifacts, prepare immutable bytes outside and register them through the Artifact owner in the current writer. If evidence or Intent changes before registration, recheck and reuse or discard preparation under the owner’s receipt rules. [Engine dispatch](gx-h/gx_core/orchestration/engine.py#L1418) · [Job guard](gx-h/gx_core/jobs/workflow.py#L10) · [Materialized artifacts](gx-h/gx_core/artifacts/service.py#L475) · [Root compute queue](gx-h/gx_core/p0/compute.py#L81)
4. **Fenced tool calls.** The existing worker extension path can prepare a calculation outside the writer, then checks the current turn, task, lease and attempt again before handing in the result and callback receipt. A calculation that can cause an external effect must use the existing proposal/Job receipt even if two callbacks race before the acknowledgment. Read-only calls need no additional user-provided idempotency key. A missing or superseded binding blocks that Run/attempt's command. [Preflight](gx-h/gx_core/p0/roots.py#L786) · [Callback and receipt](gx-h/gx_core/p0/roots.py#L821) · [Attempt-bound compute](gx-h/gx_core/p0/compute.py#L81)

The original graph and compatibility hooks predate these constraints. Binding an existing graph proves real execution through the plugin selection path. It does not by itself port that graph's SQL-using nodes or make an old dispatch callback transaction-safe. The two migration scopes and acceptance evidence are specified in the [migration map](V3_MIGRATION_MAP.md).
