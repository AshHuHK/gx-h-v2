# GX-H v3 plugin imports and versioning

Decision for P0. The source audit uses v2.1 commit `61ed0067448658e02d181b3cb85d7f68e39b6616`. Gate 0 still governs changes to the Root and workflow execution paths.

## Identity and installation

A package identity consists of its manifest ID, exact semantic version and full content SHA-256. The operator adds a `plugins` array to the existing installation document. Each record contains just `path` and `sha256`, for example `{"path":"org.example.analysis/1.0.0","sha256":"<64 lowercase hex digits>"}`. The relative path is exactly `<id>/<version>` under `gx-h/plugins/installed`. The manifest must agree with both path components. Multiple records for the same ID and version are ambiguous and fail selection of that version. A missing array means zero installed plugins. A Run selects identities from this operator catalog. Files elsewhere in the workspace never enter plugin discovery. [Existing installation configuration](gx-h/config/workflow_packages.json)

The catalog approves a specific set of bytes for in-process execution. To compute the digest, read each regular file, including the manifest, local modules, capability references and data. Sort by relative POSIX path and hash the canonical GX JSON array of pairs `[path, sha256(file_bytes)]`. The order of directory entries, install prefix, timestamps and empty directories do not affect the result. Symlinks and special files are rejected. Start at an operator-specified installation root and descend through directory descriptors without following links. Open files without following links and verify they are regular before reading. An installer can copy exactly these reviewed bytes. [Canonical GX hashing](gx-h/gx_core/domain/ids.py)

## Admission and resolution

The v1 manifest has the blueprint's eight required fields and optional author metadata. Reject unknown fields, duplicate JSON keys, mistyped values, malformed module names, duplicate declarations and incompatible GX or API versions. Plugin versions and dependency requests are exact semantic versions. The P0 host implements API `1.0` and identifies its GX release as `3.0.0`. GX compatibility uses comma-separated numeric comparisons, including the blueprint's `>=2.1,<4.0`. A dependency requests another plugin's contributions. Python bindings between plugins go through the Author API or existing owners. [Supplied manifest schema](GX_H_V3_Lean_Implementation_Package/contracts/plugin-manifest.schema.json)

Resolve the selected roots and the edges of each root in sorted `(id, version)` order. Visit dependencies before their consumers. An absent optional dependency is omitted. If its exact package is installed, its digest, compatibility and dependency checks apply. Report an ordered cycle path including the repeated vertex. Cache verified packages and shared dependency closures for this bootstrap. Validate each selected root's entire closure before importing it. Local errors identify the dependency chain. A bad unselected installation does not prevent another root from loading. A registration error leaves already successful dependencies available. Empty selection leaves existing v2.1 workspaces independent of the new importer.

## Package execution

The private top-level name begins with `gx_ext_`. It contains readable ID and version slugs and the full SHA-256 of the canonical identity tuple. This encodes punctuation and prerelease/build variants even when their slugs match. A manifest entry such as `plugin:register` resolves to `<private_name>.plugin.register`. The package spec declares `submodule_search_locations`. Standard import machinery inserts each package in `sys.modules` before its body executes. Child modules and package initializers may import siblings, parents or deeper packages by relative name. Data-only directories add no Python initialization step.

The finder handles only namespaces that GX has registered. The loader compiles Python source from the same in-memory snapshot used for the digest, including lazy imports during later tool calls. Verified bytes are immutable for the life of the loaded namespace. Source locations remain available for tracebacks and v2.1 source introspection. The importer has no filesystem search path and leaves `sys.path` intact. Pre-existing bytecode is hashed as package data and is never executed. Compiled extension modules and third-party scientific runtimes belong to the existing Capability and Job environment. Static AST checks allow standard library imports, the public `gx_core.plugins.author_api` module and plugin-local relative imports. This is an authoring policy. Reviewed, operator-pinned code runs with the privileges of the GX Python process.

Serialize publication of a new namespace and registration of that identity. The loader passes a fresh, local `RegistrationContext` to `register(ctx)`. On success, retain one frozen set of contributions with the loaded package and reuse it across simultaneous or repeated bootstraps. Each bootstrap returns its own frozen selection with dependency order and per-selection diagnostics. If import, registration or freezing raises, discard the staged contributions, remove the failing private package and its dotted children and release that namespace's finder entry. Preserve every successful peer namespace. No Run state, Job execution or external call belongs to registration.

## Ownership and integration

P0 exposes `bootstrap(install_root=None, catalog_path=None, selected=())`. A frozen registry looks up a package by ID, version and optional expected digest. Each successful record exposes the complete pin, manifest, contributions, namespace and digest-covered package files. These records describe plugin code. Workflow identity, content and historical Run pins continue through the existing workflow owner. Capability bundles and their admission remain with the existing capability and governance owners. [Workflow owner](gx-h/gx_core/orchestration/registry.py) · [Capability admission](gx-h/gx_core/capabilities/shipped.py) · [Shipped pins](gx-h/config/shipped.json)

The v2.1 workflow source digest includes Python module names and hashes of source files. Moving a binding into a private namespace changes that digest. P1 must retain the exact earlier workflow and compatible hook bindings when cold-opening a legacy Run. A newly composed Run binds its actual plugin and workflow identities. P3 persists the selected package digests, resolved closure and canonical owner pins at Run creation. On reopening, restore those exact bytes or report which dependency is unavailable for that Run. ## Acceptance consequences

Exercise two versions in one process with isolated globals, nested and lazy imports, repeat and concurrent registration. Compare the actual bytes executed after changes to on-disk source and bytecode. A canary must remain untouched for an unapproved path, digest mismatch or inadmissible manifest. Confirm cycle diagnostics, conditional optional dependencies, deterministic diamond ordering, atomic registration failure, unrelated healthy plugin use and an unchanged v2.1 project start. The existing Node/Cordis evaluator keeps its protocol and release identity.
