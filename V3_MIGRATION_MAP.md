# Migration map for the v2.1 numerical grid

The migration has two distinct deliverables. A newly created Run must be able to select a v3 plugin that binds the **actual `science_grid@2` graph**, its existing capability, and additive author contributions. A further port that relocates or changes canonical node behavior requires a new workflow version. A saved v2.1 Run must resume its original graph, compatibility hooks, Jobs and evidence. The historical source inspected for this audit is `61ed0067448658e02d181b3cb85d7f68e39b6616`, on branch `v2.1`. The recorded frozen product revision is `a05dcef64522fbbbc12120b1d78da518e6886b10`. ## Cutover and exact pins

1. **Bind a new composed `science_grid@2` Run.** The installed plugin's `register(ctx)` declares the existing graph reference and `fixture-grid@1` manifest reference, and contributes a scoped grid tool and context projection. Resolve the graph through `WorkflowRegistry`, check its actual digest and installed compatibility hook digest, and run its original five nodes, validator and completion rule. Attach only the package's additive behavior via the Run's exact composition. Do not mutate a workflow object shared by legacy Runs. Read the capability pin from its existing release/Registry owners, retaining the portable pin and store-specific manifest ref. An installation catalog needs only the install location and package digest. [Existing registry lookup](gx-h/gx_core/orchestration/service.py#L187) · [Compatibility pair verification](gx-h/gx_core/orchestration/registry.py#L66) · [Capability registration](gx-h/gx_core/capabilities/shipped.py#L42)
2. **Keep selection atomic and local to the Run.** Persist the selected package ID/version/digest, API version, actual workflow pin, capability references, closure and composition digest with the new Run, before the first advance or Root callback. A historical Run without composition uses its saved workflow selection. Resolve only the required packages for each Run; a missing pin leaves its historical status readable and isolates the unavailable behavior to dependent Runs. A warm resume reuses the same original Job/Task/Artifact receipts. Use the existing selection/admission path and one Run receipt. [Startup selection](gx-h/gx_core/orchestration/packages.py#L17) · [Run-bound restoration](gx-h/gx_core/orchestration/service.py#L169) · [Original admission checks](gx-h/gx_core/orchestration/seams.py#L329)
3. **Move active generic callers to their domain owners.** Preserve legacy science module and compatibility hook source bytes. Make the three generic imports above independent of grid-specific helpers, with coverage of the grid and geometry call sites. Convert only new external callbacks to bounded contexts. Prepare evaluation, file publication, Job submission or scientific computation ahead of transaction-bound checks at the existing owner boundaries. Do not route raw legacy `NodeContext`, full task rows or `conn` through the versioned import namespace. [Author API](V3_AUTHOR_API_FROM_SCIENCE_GRID.md) · [Callback preparation and receipt](gx-h/gx_core/p0/roots.py#L786)
4. **Version actual node changes.** If the port moves nodes/validator/compatibility handlers into plugin-local code, register the changed definition under its own canonical version, for example `science_grid@3`, and test it against v2 outcomes. Reuse the original graph layout, predicate/settlement rules, Job runtime and domain operations with narrow wrappers. Original `@2` remains a usable selection in the same process. Namespaced callables and whole module bytes participate in the existing digest; changing either changes the pin. `WorkflowRegistry.register` rejects a second content digest at the same ID/version, and `bind_compat` checks both saved hashes. A requirement to replace canonical `@2` with changed bytes while retaining its exact historical digest conflicts with both checks. An additive `@2` bridge alone leaves the SQL-based graph and original dispatch hook as legacy. Report this limitation explicitly and record any full port under its actual version. [Function names and whole-file hashes](gx-h/gx_core/orchestration/engine.py#L386) · [Graph digest](gx-h/gx_core/orchestration/engine.py#L536) · [Registry immutability](gx-h/gx_core/orchestration/registry.py#L32)

For the shipped grid, reference its existing worker and parser at their canonical paths. `registry.publish_script` and `manifest.script_path` require approved tree-relative paths and matching file hashes, and portable content includes the path. Copying the files to a plugin install directory changes this identity. A second plugin that contributes a new capability can attach an existing-format bundle pointing at installed scripts in the existing adapter roots and follow the same registry/governance path. Only release-admitted pins or ACTIVE versions can execute. A pre-existing operator draft must keep its actual status. [Allowed script roots](gx-h/gx_core/capabilities/manifest.py#L69) · [Script binding](gx-h/gx_core/capabilities/registry.py#L104) · [Admission](gx-h/gx_core/capabilities/registry.py#L385) · [Shipped grid tests](gx-h/tests/test_shipped_grid.py)
