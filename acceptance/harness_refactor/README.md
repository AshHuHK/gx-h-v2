# 科學 Lead 與 GX 的研究分工

PI 提供問題、材料、明示約束和預算。新開的普通 Goal 由 Codex Lead 決定怎麼拆題、哪些原件值得讀、要請誰協作、何時值得計算，以及何時已經可以帶著不確定性結案。GX 保存每項承諾、綁定、加入或撤回的線索、實際執行與回報。兩者的交界可以從同一份 SQLite 及具名產物複查。

完整簽收狀態、三臂的科學得分與提交成本，以及每條未完整成立的研究行為均列在[本次驗收總表](ACCEPTANCE.md)。

## 開題、繼續與取回結果

在發行目錄使用已配置的官方 Codex OAuth 宿主，普通命令如下。題面可以只寫科學問題。已有材料時，在 `--goal-config` 的 `input_files` 登記角色與檔案；有明確禁用方法或資料源的研究，保留其顯式範圍。

```bash
bin/gx-p0 research --state ./study-state --run-key first-study \
  --goal-file question.md --research-effort medium --timeout 600
bin/gx-p0 research --state ./study-state --run-id <run_id> --timeout 600
```

第一條命令回傳 Run ID。到達本次 CLI 的等待時間可沿用同一 Run 繼續。已結束的 Run 再呼叫會重導出結論和證據；仍未結束時可以查原生回合、正在執行的 Job 或等待的材料。在這個工作區啟動現場驗收，可使用附帶的啟動器配置 Clash 和既有訂閱。啟動、保存原始 session 和恢復同一題的命令見[現場操作](field/README.md)。

## 手稿如何落到正式入口

| 研究時刻 | Codex 的選擇 | GX 要保存或驗證的事實 |
|---|---|---|
| 初次遇到問題 | 查一次輕量目錄，讀選中的方法、原件、技能或既有配方；可直接採用證據，也可另找途徑。 | 區分僅參考、已安裝、本站依賴已備、此題有實際產出；記錄本站核准版本與 PI 明示限制。 |
| 探索與分工 | 按需要指定臨時研究員及交付；研究員可為自己的模組選擇方法。effort 影響初始資源及並行度。 | 每個模組有自己的可見材料、方法修訂及預算。實際派工在同一個 Job 所有者的交易中准入；未對帳作業保留原句柄與預留。 |
| 問題逐漸明確 | 用穩定意圖登記「為什麼研究」，可引證已有材料解決、綁定計算鏈或委派，也可收到反證後只重開相關路線。 | 研究意圖與執行節點共用同一版本圖。每筆已發送的 Job 保留其當時輸入與版本。 |
| 同輪研究 | 訂閱、發表、更正、撤回或綜合同行的線索；Lead 及同行自行決定採用與否。 | 按當時可見權限回放至高水位，接續之後的增量；每則訊息保留作者原話、父訊息、起源與原件。盲評研究員保持隔離。 |
| 競爭路線產出結果 | 決定哪些產物必需、哪些可互替、何時補派或停止；由新題 Lead 重新判斷如何使用成熟配方。 | Join 按具名產物的可達性喚醒，區別缺資料、技術故障、在途與真陰性。宏觀配方可保存模組、Join 與決策問題，新題對自己的輸入實際派工。 |
| 收尾 | 交代科學理由、未知事項及結論強度；可在尚有餘額時結束。 | 正式主張必須有對應的原件與量測；對明確關聯、可能改變「證據不足」結論的未核查材料，全 Run 最多提醒一次。PI 有約定時另行簽署。 |

方法的適用性由研究員依方法卡、材料及狀態判斷。站點的普通研究能力在 `gx-h/config/science_site_access.json` 以具體提供者與版本登記；插件安裝、依賴就緒、某 Run 獲准和實際拿到科學結果各有各的回執。本站實例包括文獻檢索、既有資料庫查閱與存檔資料分析。付費服務沿用站點原有的付款設定。

## 復驗與版本相容

現場示例的依賴可分別查證。酵母檔案研究在部署端讀取四份公開存檔快照；邏輯掛載位置為 `gx-h/var/science-assets/yeast-archive`，版本摘要隨插件發行。[快照摘要](../../gx-h/plugins/installed/org.gx.yeast-enzyme-archive/1.0.0/snapshots.json) 水文範例隨包保存原始 USGS 記錄、量測條件與獨立計算，兩個分析插件用標準安裝命令登記，資料及提供者回執見[水文研究](field/README.md)。

```bash
.venv/bin/python -B acceptance/harness_refactor/integration/regressions.py
.venv/bin/python -B acceptance/harness_refactor/integration/cold_upgrade.py
```

第一條走本安裝自己的 CLI、原生工具處理器、圖交易和 JobService；需要斷線或競爭的位置使用受控傳輸。第二條從完整研發基線建一個臨時部署，用基線正式入口建立並結案，再在原路徑換成候選代碼冷恢復。它核對同一 Run 的報告位元摘要、事件數和新增 Job／回合。精簡部署若沒有保存基線 Git 物件，可使用已交付的冷恢復回執與其本地相容測試。

新普通 Goal 在建立時固定 `gx.harness/2`。舊 Goal 保存舊策略，包括原來明示的空範圍。未引入新的 SQLite DDL。更新或回退前應保留資料目錄和精確的發行版本，並在沒有 Driver 寫入時備份；在原部署路徑啟動可以接回原帳本。若需回到基線，舊版 Goal 可在相應的基線代碼與相容備份恢復。已使用新意圖或宏觀配方的 Run 應以固定本版代碼繼續，或用升級前備份恢復到升級前的研究點，避免舊版誤解新動作。

完整版的普通入口驗收涵蓋三批新操作。最終產品與精簡版的 65 個共同變更檔案逐一比對，精簡站點原有的插件註冊另行核對。測試種類和實際科學鏈分開記錄。[最終部署檔案摘要](deployment/release-comparison-891a9e8.json) · [精簡版原生回合及冷重導](deployment/slim-streamflow-observation/README.md)
