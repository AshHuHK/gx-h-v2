# ADR · Promote the deployed Goal ledger to the V6.1 contract

Accepted for V6.1. The reviewed V6 implementation at `47fc728` and an online backup of observed Run 02 both contain **eight** tables with the prefix `v6_` and the ninth table `p0_v6_native_calls`. The formal DDL preserves all nine names, their keys and foreign keys, four append-only triggers and eight explicit indexes. This includes the two accounting indexes on the existing events table. SQLite supplies the additional indexes implied by primary keys and UNIQUE constraints.

| V5 concept or proposed table | Persisted V6 identity | Write authority and recovery |
|---|---|---|
| Research mandate and resource allocation | `v6_goals.run_id` referring to a Run; `goal_version` identifies its current objective | Goal startup/Intent own the mandate. A Lead may request closure and the Job reconciler records completion. The existing budget owner records limits, reservations and settlement. |
| Decision scope and commission | `v6_decision_tasks.task_id`; unique Run, scope and trigger key | Goal reactor issues the frozen decision brief. Existing Task and Lease owners fence the actual attempt, including delegated work. |

## On-disk compatibility

The released combined/DDL digest pair is `afe0646bcec1a57c36160b38a1011822258bd6cf921b26b6e5b50f18c11ff8dd` / `456753d35343e1571693a0e69d7921b75dfee0ebe653942d16eb36e842f1c4a8`. The original migrations are `v6.sql`, `v6_job_indexes.sql`, `v6_funding.sql`, `v6_native.sql` and `zzzzzzzzzz_v6_job_attempts.sql`. Their original byte digests are stored under the same `p0.migration.*` keys.

1. Native preflight checks the state marker and performs a WAL-aware, read-only check of the contract and DDL pair. The V6 pair is listed in `config/native_contract_migrations.json`.
2. On a fresh database the contract creates all business objects. At a change of contract the store holds the existing migration transaction, checks the actual CREATE statements for previously installed V6 tables, indexes and triggers and creates any objects an older release had yet to install. Missing objects for a previously recorded migration, incompatible definitions and changed migration hashes prevent restamping.
3. The P0 installer verifies the complete promoted shape before recording a pending original migration hash. A crash between the contract transaction and P0's ledger transaction can retry with the existing objects. The P0 installer still executes every other pending migration normally. Ordinary reopening keeps the existing constant-time contract check and migration-receipt lookup.
4. Graph CAS, append-only receipts, foreign keys and revision payloads are preserved. Existing rows, Jobs and budget settlements retain their original identities. A database that never saw Goal mode acquires empty Goal tables. Reopening a completed Run does not create scientific work.


A writable operator command may open a P0 ledger before its first full store open. In that transaction the P0 installer verifies existing promoted objects, creates the missing objects from unreceipted released SQL and records each original file digest. A conflicting object or a missing object for an already recorded migration aborts the transaction. The full store owner updates the global contract stamp and emits its resync event on a later full open. A read-only status command performs neither migration.

## Upgrade and rollback

Stop new admissions and quiesce the driver. Preserve a consistent whole-state backup, including the native marker, database/WAL (or an online SQLite backup), Job directories, artifacts, corresponding Codex thread store and runtime configuration. Preserve both the old executable checkout and matching dependencies. Use disposable copies for rehearsal. The native marker binds source and state paths; rehearse in an isolated deployment with stable paths or restore to the original deployment paths. Verify the restore opens under the original binary **before** upgrading. Install V6.1 and reopen through the public CLI at those same paths. Reopen a second time, check graph and claim heads, dispatch IDs, external Job contents and cost receipts. Preserve pending Jobs and reconcile the same IDs before new submissions.

For rollback stop admissions, save post-upgrade state separately, restore the complete pre-upgrade snapshot and corresponding older binary/configuration and run the old public status command. A restored snapshot can reconcile its own accepted jobs. If external effects have occurred since that snapshot, reconcile the newer ledger and provider receipts before permitting any new dispatch from the restored state.

## Decision language

The shipped revision operations are `open_branch`, `add_node`, `stop_branch`, `cancel_node` and `close_run`. `amend` uses a versioned graph base; `resolve` keeps its head and has no operations. Claim evidence directions remain `open`, `limited_support`, `contested`, `insufficient`, `mixed` and `refuted`. Maturity stages, preregistered predictions, a machine-evaluated `watch_measure` vocabulary, sealing, critics and PI signoff are future contracts. Current event watches wake a Lead to interpret changes. The existing five operations and these six directions continue to read historical payloads.
